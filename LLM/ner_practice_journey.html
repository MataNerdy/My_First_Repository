01 / Зачем

Что мы хотели получить

Модель получает предложение и выделяет в нём именованные сущности: людей, организации, места и прочие категории, предусмотренные разметкой CoNLL-2003.

Вход

«Alice Johnson joined Microsoft in London.»

Обычный английский текст, без заранее расставленных границ.

Выход

PER Alice JohnsonORG MicrosoftLOC London

Это реальные группы сущностей, найденные вручную обученной моделью после загрузки с Hub.

Использовали bert-base-cased: предобученный BERT получил новую классификационную голову для NER. Мы обучали модель для английской разметки CoNLL, поэтому результаты не следует переносить без проверки на русскоязычные тексты.

03 / Главная хитрость

9 слов превратились в 12 токенов

У первого предложения 9 меток, но токенизатор BERT добавляет [CLS] и [SEP], а слово lamb дробит на la и ##mb. Получается 12 позиций. word_ids() говорит, из какого исходного слова вышел каждый токен; служебные токены получают None.

Переключи способ разметки подтокенов

Ниже показан один и тот же вход; меняется только то, получает ли ##mb собственную метку для loss.

-100 означает «эту позицию не учитывать в функции потерь». Его получают служебные токены, padding и — в выбранном нами варианте — дополнительные части слова. У la стоит O, у ##mb — -100, после них точка опять получает O.

Почему две стратегии? Если метить каждую часть, у продолжения сущности B-ORG превращается в I-ORG. Если размечать только первый подтокен, длинное слово не начинает влиять на loss сильнее короткого. В нашем обучении использован второй способ.

Код: наша функция выравнивания
def align_first_subtoken_only(labels, word_ids):
    aligned = []
    previous_word_id = None
    for word_id in word_ids:
        if word_id is None:
            aligned.append(-100)
        elif word_id != previous_word_id:
            previous_word_id = word_id
            aligned.append(labels[word_id])
        else:
            aligned.append(-100)
    return aligned

def tokenize_and_align_labels(examples):
    tokenized = tokenizer(
        examples["tokens"], truncation=True, is_split_into_words=True
    )
    tokenized["labels"] = [
        align_first_subtoken_only(tags, tokenized.word_ids(i))
        for i, tags in enumerate(examples["ner_tags"])
    ]
    return tokenized

tokenized_dataset = raw_dataset.map(
    tokenize_and_align_labels,
    batched=True,
    remove_columns=raw_dataset["train"].column_names,
)

tokenized["labels"] по-человечески

Токенизатор создаёт input_ids и маску, но не знает правильных NER-ответов. Мы проходим по каждому предложению батча, через word_ids(i) связываем токены со словами и добавляем выровненный список правильных ответов в колонку labels.

Два уровня индексов

i — номер предложения в текущем батче. word_id — номер слова внутри этого предложения. Поэтому для батчевой токенизации вызываем tokenized.word_ids(i), а не один общий word_ids().

Для NER мы применяли seqeval: она оценивает найденные фрагменты с учётом BIO-разметки. Высокая accuracy сама по себе менее показательна, потому что большинство токенов может иметь метку O.

Что такое labels в коде

Массив формы [батч, длина] с числовыми правильными метками. «Предложение» в list comprehension — одна строка этого массива, а не строка текста.

Зачем zip(preds, gold)

Мы идём по позициям парами. Если правильная метка равна −100, эту позицию выкидываем и из ответа, и из прогноза; иначе переводим оба ID в текстовые названия.

Код: подготовка к seqeval
predicted_ids = logits.argmax(axis=-1)

true_labels = [
    [label_names[tag] for tag in gold_ids if tag != -100]
    for gold_ids in labels
]
true_predictions = [
    [label_names[pred]
     for pred, gold_tag in zip(pred_ids, gold_ids)
     if gold_tag != -100]
    for pred_ids, gold_ids in zip(predicted_ids, labels)
]
scores = metric.compute(
    predictions=true_predictions,
    references=true_labels,
)
06 / Два способа

Один BERT, два цикла обучения

В обоих экспериментах: bert-base-cased, 9 классов, 3 эпохи, батч 8, learning rate 2×10−5, T4 GPU. Это 1756 батчей за эпоху и 5268 шагов за три эпохи. Для второго эксперимента создали новую модель из базового checkpoint, чтобы не продолжать обучение первой.

A / Trainer

Готовый цикл

Передали модель, данные, collator и compute_metrics в Trainer. Он сам управлял прямым проходом, обратным проходом, шагами оптимизатора, оценкой и checkpoint.

Исходная голова для NER была новой: classifier.weight и classifier.bias отсутствовали в базовом checkpoint. Это ожидаемо.

B / Accelerate

Наш цикл

Сами написали DataLoader, AdamW, scheduler и цикл: model(**batch) → loss → accelerator.backward(loss) → optimizer.step() → scheduler.step(). Затем собирали предсказания и считали seqeval на validation.

На одной T4 Accelerator размещает модель и батчи на GPU; pad_across_processes и gather_for_metrics позволяют перенести ту же логику на несколько устройств.

Не пугаться при загрузке базового BERT: UNEXPECTED относятся к старым головам предобучения, MISSING — к новой голове NER, которую и нужно обучить. До обучения получили логиты формы [2, 12, 9] и loss около 2.15.
Код: ключевые строки ручного цикла
fresh_model = AutoModelForTokenClassification.from_pretrained(
    "bert-base-cased", id2label=id2label, label2id=label2id
)
fresh_model, optimizer, train_loader, val_loader = accelerator.prepare(
    fresh_model, optimizer, train_loader, val_loader
)

for epoch in range(3):
    fresh_model.train()
    for batch in train_loader:
        optimizer.zero_grad()
        loss = fresh_model(**batch).loss
        accelerator.backward(loss)
        optimizer.step()
        scheduler.step()

    fresh_model.eval()

Разница между test F1 двух запусков — около 0.0029. Validation у обоих выше test. Значит, показатель с validation не следует выдавать за финальное качество на отложенной выборке. Два разных прогона не являются идеально контролируемым сравнением API: случайная инициализация головы, порядок батчей и детали оптимизатора могут различаться. У Trainer лучший validation F1 был после 2-й эпохи (0.9503), но показанный test получен после 3-й.

Мы отдельно проверили, что для финальной оценки действительно использовались 3453 test-примера, а не те же 3250 validation-примеров с переименованными ключами метрик. Это исправило один из самых коварных моментов практики.
